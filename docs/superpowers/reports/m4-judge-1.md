The Dockerfile neutralises that (`sed -i 's/\r$//'` at `fairmatch/Dockerfile:27`, which I confirmed restores a CRLF copy byte-for-byte to the LF original). nginx accepts CRLF configs, and Dockerfile/YAML parsers accept CRLF. ## Check 2: nginx.conf

No nginx binary on this machine and the Docker daemon is off, so `nginx -t` was not run. Judged by reading.

Evidence:
- The SPA calls `fetch(`/api${path}`)` (`frontend/src/api/client.ts:84`). Its paths are `/auth/login`, `/auth/register`, `/candidates[/me|/:id|/:id/demographics]`, `/opportunities[/:id|/:id/similar-candidates?limit=]`, `/runs[?limit&offset]`, `/runs/:id` and `/runs/:id/explanations`, and they match the FastAPI routes exactly (`@router.post("")` with prefix `/runs`, and so on). No trailing-slash redirect is triggered, which matters because a FastAPI redirect would lose the `/api` prefix. `location /api/` + `proxy_pass http://api:8000/;` turns `/api/runs?limit=20&offset=0` into `/runs?limit=20&offset=0`, so query strings survive. Multipart is proxied with nginx's default request buffering (temp files go to `/tmp` in nginx-unprivileged). `/api` without the slash falls through to the SPA; the client never calls it.
- `add_header` inheritance: the server-level headers are dropped by any location that has its own `add_header`. The file repeats all five security headers in every location, with `always`, so 404/413/502 responses carry them too. Correct.
- 413: `client_max_body_size 6m` sits at http level (the file is included from conf.d inside `http{}`). Bodies over 6 MiB with a `Content-Length` are rejected before upstream is contacted, so the API writes nothing. nginx's 413 body is HTML. The client handles that: `errorFor` falls back to `Request failed (413).`. The UI also pre-checks 5 MiB (`frontend/src/lib/validation.ts:2,30`).
- SPA fallback vs assets: `/assets/` uses `try_files $uri =404` with an immutable cache header. Everything else uses `try_files $uri /index.html` (an internal redirect re-matched by `location /`, so index.html gets `no-cache`). Missing chunks are real 404s, and the ErrorBoundary at the top (`src/components/ErrorBoundary.tsx`) catches the rejected lazy import and offers Reload, which covers a stale tab after a redeploy.
- CSP vs the built app: `index.html` has no inline script, the favicon is `data:,` (allowed by `img-src data:`), there are no external fonts, no `blob:`/`createObjectURL`/Workers in `src/`, and Recharts inline style attributes are allowed by `'unsafe-inline'`. No websocket is used.

The probe is also misattributed: it is zod v4's `allowsEval` JIT check (`new Function("")` in try/catch, with the Cloudflare UA check), not react-router. ## Check 4: Reclaim logic (runs.py, worker.py, migration 0002)

Evidence:
- `pytest tests/api/test_reclaim.py tests/test_docker_files.py tests/test_compose_file.py tests/test_ci_workflow.py`: 37 passed. Full backend suite (`-m "not slow and not llm and not db"`): 311 passed, 4 deselected. `ruff check .`: clean. `python scripts/export_openapi.py --check`: up to date. The OpenAPI diff since 05d05ac is exactly `started_at` (nullable date-time, required) added to `RunSummaryOut` and `RunOut`. `schema.d.ts` matches. The frontend types it, and the run JSON is not validated by a strict zod object, so the extra key is harmless; it is not displayed anywhere.
- Adversarial probes (scratchpad `probe_reclaim.py` and `probe_redis_migr.py`, run against a file SQLite DB):
  - P1: the default `created_at` (aware `datetime.now(UTC)`) is stored as a UTC wall clock on SQLite. A fresh pending run is not reclaimed; at now+6 min it is. PASS.
  - P2: an aware non-UTC `now` (IST +05:30) is converted, not truncated. A fresh running run is not reclaimed and an expired one is. PASS. (P2c: an aware IST `started_at` written through the ORM is stored as the IST wall clock on SQLite, with the tz dropped. The code never does that, since it writes `_naive_utc()`, so this is informational.)
  - P3: a duplicate `execute_run` delivered mid-run does no work, and the first run finishes `done` with one allocation set. PASS.
  - P4: reclaim racing a concurrent claim. **FAIL**: see F14.
  - P5: an old `pending` run is returned on every reclaim (3/3), so every worker start re-enqueues it. Harmless only because the claim is idempotent.
  - P6: a stale duplicate message re-executes a `failed` run (`failed` to `done`). This comes from the claim accepting `failed`, which predates M4, but reclaim makes duplicate messages routine.
  - P7a/P7b: `worker_ready` with the DB down, or Redis down, never raises. With Redis down the expired run is left `pending` for the next start. But the handler runs synchronously in the worker's main thread and took 131.5 s (psycopg's default 130 s connect timeout; Windows refused-port behaviour) and 75.2 s (kombu publish retries) here.
  - P8: migration 0001 to 0002 to 0001 on SQLite with existing users, candidates, opportunities, 3 runs and 1 allocation: all rows survive both directions, `PRAGMA foreign_key_check` is clean, and the FK list of `allocation_runs` is unchanged after the batch table rebuild. A second `upgrade head` on an up-to-date DB is a no-op. PASS.
- PostgreSQL reasoning: `started_at` is written as naive UTC and compared in SQL against naive UTC, so it is TZ-independent. `created_at` is written as an aware datetime into `timestamp without time zone`. psycopg sends `timestamptz`, which PostgreSQL casts using the session `TimeZone`. In the compose and CI pgvector images `TimeZone=UTC`, so it is consistent. On a non-UTC PostgreSQL server (e.g. a local Windows install in IST), `created_at` would be stored 5:30 ahead and old pending runs would not be picked up for hours (F17).

Findings:
- F13 MAJOR `fairmatch/api/worker.py:89-109` (design): reclaim runs only on `worker_ready`. With `restart: unless-stopped` (`docker-compose.yml:59`), a killed or OOM-killed worker container is back within seconds. At that moment the orphaned run's `started_at` is fresh (under 30 min), so it is not reclaimed, and Celery's default early ack means its message is already gone. The run then stays `running` until some worker happens to start 30+ minutes later. The same applies when only a prefork child dies (OOM on a large run): the main process survives, `worker_ready` never fires again, and the run is stuck indefinitely. The Review Focus case ("killed mid-way ... must be reclaimed and finish") is met only if the restart happens after the timeout. Fix: a periodic sweep (e.g. a timer thread started in `worker_ready` that calls `reclaim_stuck_runs` every few minutes, or celery beat), and cap run duration with `task_time_limit` below `run_timeout_minutes` so a live run can never look expired.
- F14 MINOR `fairmatch/api/services/runs.py:71-84`: reclaim reads rows, then writes `status='pending', started_at=NULL` through the ORM (`UPDATE ... WHERE id=?`, with no status or started_at guard). Probe P4 interleaved a second worker's claim between that read and the commit: reclaim overwrote the fresh claim back to `pending`, cleared `started_at` and returned the id for re-enqueue, which gives a second concurrent execution of a fresh run. The window is milliseconds and needs at least 2 worker instances starting together. Fix: a single guarded `UPDATE ... WHERE status='running' AND (started_at IS NULL OR started_at < :cutoff)` (with `RETURNING id` on PG, or re-check `rowcount`).
- F15 MINOR `fairmatch/api/services/runs.py:104-130`: there is no liveness signal besides the timeout. A legitimate run longer than `run_timeout_minutes` (runs of up to 25M cells, or slow LLM explanations, are allowed) is taken over by any reclaim or redelivery and executed twice. On PostgreSQL, the loser hits `uq_allocation_run_algo_cand` on insert, and `mark_failed` can then overwrite the winner's `done` with `failed`. Same fix as F13 (time limit plus heartbeat or periodic sweep).
- F16 NOTE `fairmatch/api/worker.py:89-109`: the handler blocks the worker main thread during startup (P7: 131 s with the DB unreachable, 75 s with Redis down, on this Windows box; Linux refuses faster, but an unroutable host would still hit the 130 s default). Consider running it in a daemon thread and/or `connect_timeout`.
- F17 NOTE `fairmatch/api/models.py:11,68`: `created_at` default is aware into a naive column, and its stored value depends on the PostgreSQL session TimeZone. That is fine in the shipped images (UTC). For robustness, write `_naive_utc()` like `started_at`, or set `options=-c timezone=UTC` on the engine.
- F18 MINOR `fairmatch/tests/api/test_reclaim.py:59-63`: `test_aware_now_and_aware_started_at_compare_safely` passes a naive `started_at`, so the aware-started_at case in its name is not tested. The migration test only covers an empty DB (P8 above covers data). No test exercises the reclaim/claim race (P4) or the PostgreSQL path of reclaim.
